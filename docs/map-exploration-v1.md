# ระบบสำรวจรุ่นแรก

ผู้เล่นเปิดหน้า `/exploration` เลือกจุดจากภาพอาคารหรือภาพประตู เลือกไปเองหรือผู้ติดตาม แล้วส่งงานเข้าคิวทีมงาน ทีมงานทอยและสรุปผลผ่านเมนูภารกิจสำรวจ รางวัลเข้าคลังเดิม และใช้ผ่านคำร้องใช้ไอเท็มเดิม

## เปิดใช้งานฐานข้อมูล

รัน migration ตามลำดับบนฐานข้อมูลที่มี migrations เดิมครบแล้ว:

1. `20260929000000_map_exploration_v1.sql`
2. `20260929001000_seed_palace_map.sql`
3. `20260929002000_remove_exploration_quotas.sql`
4. `20260929003000_exploration_location_notes.sql`
5. `20260929004000_player_exploration_outcome.sql`
6. `20260929005000_player_exploration_drop_number.sql`
7. `20260929006000_backfill_exploration_drop_numbers.sql`

ถ้าติดตั้งถึงรายการที่ 5 แล้ว ให้รัน `public/setup/enable-one-click-exploration.sql` ใน Supabase SQL Editor ไฟล์นี้ติดตั้งการสุ่มผลและเลข d100 พร้อมกันเมื่อผู้เล่นกดสำรวจ และเติมเลขให้ภารกิจเดิมที่สำเร็จแต่ยังไม่มีเลข ผู้เล่นเห็นเพียงสถานะรอสต๊าฟ สต๊าฟเห็นผลกับเลข d100 และเลือกของจากคลังเองตามโน้ตพื้นที่ ไม่มีตารางจับคู่เลขกับไอเท็มอัตโนมัติในขั้นนี้ หากติดตั้งรายการที่ 6 แล้ว ให้รันเฉพาะรายการที่ 7

ระบบสุ่มสำเร็จ/ไม่สำเร็จตามเปอร์เซ็นต์จริง เช่น 50% คือโอกาสครึ่งหนึ่งทุกครั้ง ไม่ใช้เกณฑ์เลขเต๋า Talent เป็นตัวคูณของโอกาสพื้นฐาน เช่น ฐาน 50% และ Talent +40% เป็น 70% (สูงสุด 95%, ต่ำสุด 5%) คำขอเดิมกดซ้ำไม่เปลี่ยนผล สต๊าฟยังเลือกไอเท็มและสรุปผลเอง

ถ้าติดตั้งระบบแผนที่แล้วและต้องการเพิ่มช่องโน้ตทีมงาน ให้รันเฉพาะ `public/setup/add-exploration-location-notes.sql` ใน Supabase SQL Editor โน้ตเก็บแยกจากข้อมูลที่ผู้เล่นอ่านได้

ถ้าติดตั้งสองรายการแรกแล้ว ให้รันเฉพาะ `public/setup/remove-exploration-quotas.sql` ใน Supabase SQL Editor เพื่อเลิกใช้รอบและโควตา โดยไม่ลบงาน ประวัติ หรือไอเท็มเดิม

migration ที่สองเพิ่มข้อมูลสถานที่ตามภาพ 48 จุด โดยพื้นที่ใหม่ปิดไว้ก่อน ไม่มีการลบพื้นที่เดิมหรือแจกสิทธิ์อัตโนมัติ รหัส `zone_number` เดิมไม่ใช่หมายเลขบนภาพ; ใช้ `map_label` เช่น `6.1` หรือ `A` ผูกภาพกับข้อมูล

ทีมงานเปิดเมนูแผนที่ เลือกจุด กำหนดเปิดใช้งาน และเลือกตัวละครที่ไปเองได้ ผู้ติดตามใช้ `access_areas` และ Talent จากทะเบียนเดิม ไม่มีระบบรอบ โควตารายวัน/สัปดาห์ หรือตัวนับจำนวนครั้ง เมื่อส่งงานแล้วรอทีมงานปิดงานก่อนส่งใหม่ตามขั้นตอนเดิม

ถ้ายังไม่มีคอลัมน์ `map_label` / `self_character_ids` หน้าจัดการจะตรวจพบก่อนบันทึกและส่งเฉพาะข้อมูลพื้นที่เดิม ช่องผูกจุดและสิทธิ์ไปเองจะปิดไว้โดยมีข้อความอธิบาย ไม่แจ้งว่าบันทึกสิทธิ์สำเร็จ สามารถกดดาวน์โหลด SQL ติดตั้งจากหน้านี้ แล้วรันใน Supabase SQL Editor ครั้งเดียวและกดตรวจสอบอีกครั้ง ไฟล์รวม migrations สองรายการด้านบนและคำสั่ง reload schema ไม่มีการรัน SQL จากหน้าเว็บโดยตรง

## ผลและไอเท็ม

- โอกาสไปเองใช้ค่าพื้นฐานของสถานที่ ยังไม่สมมติระบบ Talent ตัวละครที่ไม่มีในฐานข้อมูล
- ผู้ติดตามใช้การคำนวณ Talent เดิมฝั่งเซิร์ฟเวอร์
- ผู้เล่นกดสำรวจแล้วระบบสุ่มสำเร็จ/ไม่สำเร็จทันที ถ้าสำเร็จจะสุ่มเลข d100 ในครั้งเดียว ผู้เล่นเห็นเพียงว่ากำลังสำรวจและรอสต๊าฟ ทีมงานเห็นผลกับเลข เลือกไอเท็ม และเขียนสรุป รุ่นนี้ยังไม่สุ่มตารางดรอปอัตโนมัติ
- งานจากแผนที่สำเร็จรับได้ไม่เกินหนึ่งชิ้น งานล้มเหลวรับของไม่ได้
- ปิดงานและมอบของในธุรกรรมเดียว ปิดซ้ำไม่ได้ คำขอเดิมส่งซ้ำด้วย request UUID เดิมได้โดยไม่สร้างงานซ้ำ
- รายละเอียดสำหรับสต๊าฟไม่ส่งในผลภารกิจผู้เล่น
- ใช้และโอนไอเท็มผ่านระบบเดิม ไม่มีรายงานสืบคดี คราฟท์ หรือรูทต่อเนื่องในรุ่นนี้

## ขอบเขตและทดสอบ

ทั้งสองแอปยังใช้ระบบบัญชีเดิม: หน้า player ระบุตัวละครด้วย `characterId` และ RPC เดิมอนุญาตบทบาท anon ฟีเจอร์นี้ไม่ได้เพิ่มการยืนยันตัวตนแบบ Supabase Auth ให้ผู้เล่น การออกของและสรุปผลยังจำกัดสต๊าฟ ไม่ควรถือว่ารหัสตัวละครใน localStorage เป็นหลักฐานยืนยันเจ้าของบัญชี

`npm run test:exploration` ฝั่งทีมงานใช้ PGlite จำลอง PostgreSQL ทดสอบ migrations กับ baseline ย่อ: สิทธิ์พื้นที่ เจ้าของผู้ติดตาม คำขอซ้ำ การสุ่มผลโดยผู้เล่น สิทธิ์สต๊าฟ การยกเลิก และการมอบของแบบ atomic ไม่มีการติดต่อฐานข้อมูลจริง

ฝั่งผู้เล่นมี `npm run test:exploration` ตรวจ 48 จุด การจับคู่พื้นที่ การเรนเดอร์สองภาพ และการปิดปุ่มส่งงานเมื่อยังไม่เข้าสู่ระบบ การตรวจแบบนี้ไม่แทนการทดสอบหน้าจอและการเชื่อมต่อฐานข้อมูลจริง
